| 1 | 09-26 | One repo, one folder per area (`infra`, `docs`, `frontend`, `backend`, `ml`, `data`, `evals`) | One place for the team and the judges |
| 2 | 09-27 | Focus on the **contact center** (first contact resolution, agent performance, sentiment). Credit-eligibility agent dropped | The dataset is rich in contact center data; one flow done well |
| 3 | 09-27 | Data lake: S3 (`data-root` = original data, never modified; `hackaton-data` = our results) + Glue catalog + Athena | Costs cents; nothing to run or maintain |
| 4 | 09-27 | Clean and model data with **dbt SQL on Athena**, not Glue jobs | About 10–100x cheaper at our size; SQL is easier for everyone |
| 5 | 09-27 | Star schema with **`fact_interaction`** at the centre. FCR = resolved and no repeat contact on the same topic within 7 days | Standard, defensible metric |
| 6 | 09-26 | Keep original data untouched and keep nulls. Don't use the organizers' `data_backup_20260831` | It's a different version of the data with different IDs |
| 7 | 09-27 | No names, documents, contact details or addresses in the cleaned tables | Security first; the repo is public |
| 8 | 09-27 | Agent built with **LangGraph + LangChain** | Security rules enforced in code, not just in the prompt |
| 9 | 09-27 | **Bedrock** in production; **OpenRouter** free models only for local development, with test data only | Bedrock: no API keys, data stays in AWS. OpenRouter: $0 while building |
| 10 | 09-27 | Cost limits: budget alerts (set up manually in the AWS console), 10 GB cap per Athena query, no always-on services, train models on laptops | We pay for AWS |
| 11 | 09-27 | Terraform state kept on Paul's laptop for now | Only Paul changes infrastructure |
| 12 | 09-27 | ML starts with scikit-learn and simple baselines; add other libraries only if they prove better | Simple first, no extra installs |
| 13 | 09-27 | Team access through personal **IAM users with access keys** (group `hackaton-team`), created manually. Replaces the SSO plan | Quicker to set up for a 10-day project. One key per person, never shared; delete users and keys after Oct 16 |
| 14 | 09-27 | Terraform only creates stable infrastructure (buckets, Glue databases, Athena workgroup). All tables, raw and curated, are managed with dbt | The data team can change tables without Terraform or infrastructure access |
| 15 | 09-27 | `call_transcripts` is read from a Parquet copy (`data/scripts/convert_transcripts.py`), not the CSV | Every transcript has line breaks in its text; Athena split them into ~925k broken rows. The original CSV stays untouched |
| 16 | 09-27 | MVP chat uses **Hugging Face Inference Providers** (free tier, `openai/gpt-oss-20b` through the OpenAI-compatible router) for local development. Replaces OpenRouter there (row 9). Production stays Bedrock only: the app refuses to start with `APP_ENV=prod` and another provider. Only synthetic/test text is sent to HF | One client (`ChatOpenAI`) gives streaming and tool calling. The free tier is only $0.10/month, so tests and evals use a fake model; switch to Bedrock before full eval runs |
| 17 | 09-28 | Bedrock model: **Claude Haiku 4.5** via the US cross-Region inference profile `us.anthropic.claude-haiku-4-5-20251001-v1:0`, region us-east-2, through `langchain-aws` `ChatBedrockConverse`. Configurable with `BEDROCK_MODEL_ID` | Cheapest current Claude ($1/$5 per M tokens) for a contact-center chat; swap to Sonnet via config if quality needs it. The bare model ID is not supported on demand, so the inference profile is required |
| 18 | 09-28 | Every chat turn is recorded with its metrics (tokens, time to first token, total time, errors) and the customer's 👍/👎. Local: JSONL file (gitignored). Deployed: **DynamoDB** on-demand, PK `session_id`, SK `message_id`, TTL 30 days. Card/account numbers and emails are masked before storing; logs carry numbers only | Measures quality and cost per turn and turns bad replies into eval cases (EDD). DynamoDB on-demand costs cents at demo volume and is already in the architecture; Athena is for analysis, not for the live path |
| 19 | 09-28 | Hosting: **CloudFront** in front of a private **S3** bucket (frontend) and a **Lambda function URL with response streaming** (FastAPI through Lambda Web Adapter, arm64), same origin. Terraform in `infra/app` creates it once; `deploy.yml` ships code on every push to `main` through GitHub OIDC | Scales to zero and stays in the free tier at demo volume (vs ~$26+/month for ECS Fargate + ALB). Streaming keeps SSE token by token. Same origin means no CORS; a secret header keeps the public function URL behind CloudFront |
| 20 | 09-28 | Spend limits on the public chat: **$5/day** model budget for the whole app (charged with the tokens each turn reports) and **30 messages/hour per visitor IP** (CloudFront-Viewer-Address, stored hashed). Over a limit the API answers `429` without calling the model. Counters are atomic updates in the interactions table | The demo link is public, so anyone could run up the Bedrock bill. The app-side cap stops spend in real time (AWS Budgets data lags by hours) at no extra cost; the per-IP limit keeps one script from using the whole day's budget |
| 21 | 09-29 | Sessions and conversation history in **DynamoDB** (`fh26-chat-sessions`, one item per session, on-demand, TTL 24 h after the last message). The agent loads the history, runs the stateless LangGraph graph and saves the turn; last 40 messages kept. Replaces the in-memory store and `InMemorySaver` | Lambda instances don't share memory: conversations reset on cold starts and between parallel users. A LangGraph DynamoDB checkpointer adds a dependency and its own table schema for a one-node graph; storing the messages is simpler to read and audit. Short TTL keeps raw conversation text only while the chat is active; the 40-message cap bounds item size and input tokens |
| 22 | 09-29 | **Identity verification in code** (`auth_gate` node): document number → date of birth (KBA) → 6-digit OTP. The model only calls a `start_identity_verification` tool; pending steps skip the model, answers are never sent to it nor stored (placeholders). Same reply for unknown and known documents; 3 failures lock the session; OTP hashed with salt, 5 min; verification lasts 30 min. Demo: 2 fictional customers and the OTP shown as a demo SMS (`notice` event) | Security first: the LLM can decide *when* to ask, but only code decides *who* is verified, so prompt injection can't skip it. Real SMS (SNS) costs money and needs sandbox approval; a visible demo code lets judges try the flow. Customer identifiers are excluded from `latam_curated` on purpose, so the real directory needs a team decision (see `docs/demo.md`) |
| 23 | 09-29 | dbt **dev/prod targets**: `dev` (default) builds into `latam_curated_dev_<name>`; `prod` (`latam_curated`) is built only by `.github/workflows/data.yml` on merges to `main`, through a least-privilege OIDC role (`fh26-github-dbt`: read raw, write only `latam_curated`, capped workgroup). CI runs `dbt parse` on PRs. No partitioning/incremental models yet | Anyone running `dbt build` used to overwrite the tables notebooks and the app read. Performance doesn't need tuning: the full model builds in ~1 min for cents and Parquet already prunes columns; partitioning 4.4M rows would only create small files. Incremental loading is kept for the freshness/late-arrival evidence (see data/dbt/README.md) |
| 24 | 09-29 | **The whole dataset in DynamoDB** (`fh26-demo-customers`, on-demand): one partition per customer with `PROFILE`, `PRODUCT#`, `TXN#` and `COMPLAINT#` items (~5.1M items), a sparse `by-document` index for the login, and an index item with the demo scenarios and a pool of random customers. `data/scripts/load_demo_data.py` exports with Athena `UNLOAD` (Parquet) and writes in parallel batches; reruns overwrite. Identity comes from `latam_raw`, the rest from `latam_curated`. The Lambda only reads | The agent can't query Athena per message (seconds and scan cost). Loading every customer (~$3-7 once, < $1/month) means any `customer_id` of the dataset works, so judges can check answers against it; lookups read one partition, so size doesn't change latency. The dataset is fully synthetic, so identifiers may be stored here; `latam_curated` still excludes them |
| 25 | 09-29 | **Realistic web login + demo panel** (replaces the chat-only demo): country, document type and number, password, then a 6-digit code by (demo) SMS; the login creates the chat session already **verified**, so Nova doesn't ask again ("path A"). All demo customers share one published password; the code is what proves identity. A separate, clearly labeled **demo panel** lists scenario customers (declined payment, open complaint, past due, random) and finds any `customer_id`, and fills the form. A session created later is bound to its customer and only inherits a *verified* login session | A bank app authenticates once at login; asking again in the chat looked artificial. Real accounts (Cognito) or SMS (SNS) add setup and cost without improving the demo; the challenge accepts a trusted test session. The panel keeps the bank's screens realistic while judges still get test customers in one click. The chat's own verification (decision 22) stays for expired sessions and for a future public channel |
| 26 | 09-29 | **Account tools for the verified customer**: `get_my_products`, `get_my_transactions` (days, status, text search; declined ones with their reason) and `get_my_complaints`, reading the customer's DynamoDB partition. The model only gets them once the session is verified, none takes a customer id (the graph's `account_tools` node uses the session's), at most 3 tool rounds per turn, and results carry only banking-app fields (no fraud labels, no internal ids). "Today" is the dataset's last day (`DATA_AS_OF_DATE`, 2026-06-17). **No public chat channel** ("path B" dropped): the chat lives inside the logged-in app | Tools without an id parameter make "someone else's data" impossible to request, whatever the prompt says; checking verification again in code covers expiry mid-turn. Single-partition queries keep each lookup to milliseconds and fractions of a cent. The data is a snapshot, so anchoring dates to its end keeps "last 30 days" meaningful. A second, anonymous channel would double the security surface without helping the demo |
| 27 | 09-29 | **Handoff to a human agent**: the model calls `request_human_agent` (reason, its own summary, open questions); code builds the case with the **verified facts from the session** and the **evidence from the account tools actually run**, never from the model's words. While the case is open the bot stays out (`human_queue` node): customer messages go to the case, the agent answers from the **agent console** (`/asesor`, shared demo key), and the chat polls for the replies every 3 s. Cases in DynamoDB (`fh26-handoff-cases`, TTL 7 days). Unsupported requests: explain, or hand over to a person who can do it; ambiguous ones: one clarifying question. Chat header: download, restart, minimize, and close with a confirmation that offers to download or email (`mailto:`) the conversation. No WhatsApp channel | The challenge asks for handoff with request, verified facts, actions, evidence and open questions; building facts and evidence in code means the agent can trust them even if the model is wrong or manipulated. Polling fits Lambda (no long-lived connections) at demo volume. WhatsApp (Cloud API: verified Meta business, dedicated number, templates, webhook) was dropped: days of setup for the same demo effect; real email needs SES (sandbox, cost) |
| 28 | 09-29 | **Agent console as an admin dashboard with a faithfulness view**: three columns (ticket queue with counts and average faithfulness; the dialog, Nova's conversation then the agent's; the case context). For each of Nova's answers in a handed-over case, `backend/app/agent/faithfulness.py` compares it with the evidence it consulted: **checkable claims** (numbers, dates, last 4 digits, names) marked ✓ found / ✗ not found in the tool results, a score = supported / total, and a **heatmap of cosine similarity** between each sentence and each evidence item using term-frequency vectors (shared tokens on hover, table view). English dataset codes count with their ES/PT translations ("Active" backs "Activa") | The agent has to trust what Nova told the customer before acting on it; a per-token view shows exactly which figures came from data and which didn't. Term vectors are deterministic, free and explainable (no model judging a model, no new AWS service). Known limits, shown in the UI: it checks grounding, not correctness (a real number from the wrong row still matches: seen live, Nova attributed a declined purchase to the credit card instead of the savings account), and it misses paraphrases; Bedrock embeddings could replace the vectorizer |
| 29 | 09-30 | **Learned component: intent classifier on the customer's words** (`backend/app/agent/intent.py`, model card in `ml/README.md`). TF-IDF (word + char n-grams) + logistic regression maps each chat message to the dataset's `reason_category` (6 reasons) or `other`, trained with scikit-learn on team-written ES/PT phrases and run in plain Python in the Lambda from a JSON export (parity test with scikit-learn). Each reason carries the bank's real FCR rate from `fact_interaction`; for confident complaints (43%) and retention (60%) the turn's prompt tells Nova to offer a human sooner. The intent goes into the case, the agent console and each turn's log. Held-out test (210 phrases, written separately): macro-F1 **0.85** vs 0.62 for keyword rules and 0.04 for the majority class | The planned model on the bank's transcripts was impossible: `customer_text` has only 42 distinct texts spread evenly over all reasons, and fraud, complaint SLA and resolution-by-history targets are also flat (all checked, listed in the model card). Reason → resolution is the dataset's one real pattern, and the reason is what Nova doesn't know at chat time. A small linear model is free to run, explainable and ~0.3 ms per message; the LLM could classify too, but the routing decision stays in code and testable. Limit: trained and tested on team-written text, not real chats |
